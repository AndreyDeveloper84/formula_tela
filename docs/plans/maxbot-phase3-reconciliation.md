## R1. Главное меню — оставляем 3-кнопочное

**Spec v1 (§14):**
> UX-ошибки (запрещено): главное меню; 5+ кнопок; сложные формы.

**Design Doc (§4.1):**
> 3 кнопки главного меню: `[📅 Запись в салон] [🍎 Дневник питания] [💬 Задать вопрос]`. Порядок: запись первой (revenue priority).

**Решение: Design Doc, c уточнением.**

**Почему:**

1. **Бизнес-контекст ≠ generic AI-консьерж.** Spec v1 написан как обобщённый «*персональный AI-консьерж*» (§1) — но «Формула тела» это не SaaS-стартап с одним продуктом. **У бота две функции с разными конверсионными воронками:** (а) запись в салон (revenue, средний чек 3-8к ₽), (б) nutrition (growth-канал). Принципиально нельзя скрывать запись за «дневником» — это убьёт revenue-priority.
2. **Existing user behavior data.** Текущие BotUser'ы уже знают что бот = «запись в салон». Удаление кнопки записи = регрессия для всех `bookings_count >= 1`.
3. **Spec v1 §1 говорит «не меню-бот»** — мы согласны. **3 кнопки ≠ меню-бот.** Меню-бот = иерархия 5+ функций. 3 кнопки = trichotomy revenue/growth/catch-all, каждая ведёт сразу в action.
4. **«Не выбор функций — только цели» (§3.3 Spec v1)** — да, **внутри** дневника цели первичны (что даст нам §3 анкеты). Но на корне бота — **режимы**, а не цели. Это два разных уровня.

**Уточнение к Design Doc §4.1:**

Текущая формулировка `[💬 Задать вопрос]` теряет цель. Spec v1 правильно подсвечивает что catch-all-кнопка должна звать в диалог, а не в FAQ. **Меняем на `[💬 Спросить меня]`** или `[💬 Помочь подобрать]` — тестим в копи-полировке.

**Action:** Design Doc §4.1 остаётся, в копи-полировке UX-копи (Шаг 4 из §17 Design Doc) пересмотреть лейбл третьей кнопки.

## R2. Первичная развилка — функциональная, но welcome-текст с «целевыми» хуками

**Spec v1 (§5):**
> Кнопки: `[Хочу похудеть] [Просто посмотреть] [Записаться]`. UX: нет меню, только цели.

**Design Doc (§4.1):**
> Профильная развилка по `BotUser.bookings_count` + history. Возвращающийся клиент: «*Анна, привет! Кстати, я теперь умею вести дневник — настроим? / Не сейчас*». Молчун: «*…не только записывать, но и считать калории — попробуем?*». Новый: 3-кнопочное меню.

**Решение: Design Doc, но welcome-text для нового пользователя усиливается «целевым» хуком.**

**Почему:**

1. **Spec v1 смешивает функцию (Записаться) с целью (Похудеть) с состоянием (Посмотреть).** Это плохая taxonomy — `[Записаться]` это revenue funnel, `[Похудеть]` это разговорный entry в анкету, `[Посмотреть]` это nothing-button. У них разные шаги дальше.
2. **«Похудеть» нерелевантно ~40% аудитории.** Spec v1 §2 сама признаёт ЦА = «*женщины 23-45*», но женщины 23-45 в Пензе приходят в салон **за разным**: похудеть, антистресс, восстановиться после родов, подтянуть фигуру (≠ похудеть), убрать боли в спине. Кнопка `[Похудеть]` отрезает большую часть.
3. **Design Doc §4.1 уже учитывает варианты ЦА** через `bookings_count + history`. Это сильнее чем 3 цели.
4. **Целевой хук в копи** (а не в кнопке) даёт лучшее: первый user-message на free-text «*хочу подтянуть фигуру к лету*» → `ai_assistant` → `recommend_services` (Phase 2.4 уже есть). Кнопки **дублируют** этот путь — всегда хуже.

**Уточнение к Design Doc §4.1 — welcome для нового пользователя:**

Текущий design не показывает exact текст welcome для нового. Вписываем:

```
🌿 Привет!

Я бот «Формулы тела». Помогу записаться,
посчитать калории и подсказать как
прийти в форму.

С чего начнём?

[📅 Запись в салон]
[🍎 Дневник питания]
[💬 Спросить меня]
```

«*Прийти в форму*» — Spec v1 хук (полезен), но без сужения до «похудеть». Free-text после welcome всегда работает (ai_assistant ловит).

**Action:** Уточнить exact welcome-текст в copy-polish stage Design Doc §17 шаг 4.

## R3. Мини-анкета — Design Doc, но MVP-cut TIER-A

**Spec v1 (§6 шаг 1):**
> Мини-анкета (диалог): возраст / рост / вес / цель + кнопка `[Пропустить]`. По одному вопросу, без формы.

**Design Doc (§4.3-4.5):**
> 16-шаговая `NutritionAnketaStates`: consent → gender → age → height → weight → goal → goal_pace → goal_gain_clarify → 6 health-screens → complete.

**Решение: Design Doc как target, но MVP staged.**

**Phase 3.1 MVP — TIER-A (4 базовых шага, ближе к Spec v1):**

```
consent → gender → age → height → weight → goal → goal_pace → complete
```

(Без health screening. Disclaimer-consent есть — там же ack 152-ФЗ для базовой обработки данных.)

После TIER-A → расчёт нормы + первое фото. Health-screening **отложен на Phase 3.2** или вызывается **по триггеру** (когда AI собирается дать advice — gate из принципа №4 Design Doc §1).

**Phase 3.2 — TIER-B (health screening, on-demand):**

Не в анкете заранее, а **lazy** — когда AI готов выдать рекомендацию (БЖУ-совет, добавки, weekly insight) и видит `disclaimer_acked == null OR health_flags == {}`, он **в этот момент** говорит:

```
🤖 Хочу подсказать по белку — но сначала
   пара уточнений (15 секунд), чтобы
   совет был безопасным.
   
   [Окей] [Не нужно, понятно так]
```

**Почему:**

1. **Spec v1 §3.1 — «минимум шагов»** правомерно критикует 16-шаговую анкету сразу на входе. Юзер не дойдёт до wow-момента, отвалится на шаге 3.
2. **Design Doc §1 принцип №4: «health screening — gate для советов, не для базового учёта».** Это **уже** разрешает lazy подход — формулировка просто не довела до логического конца («если screening = gate, давай его на gate, а не до loop'а»).
3. **TIER-A покрывает 80% value:** BMR + норма ккал + БЖУ + норма воды считаются на gender/age/height/weight/goal. Без health-flags расчёт *безопасен* (нет override на pregnancy / eating_disorder, но и нет советов которые могут навредить).
4. **Эскалация в TIER-B обоснованная** — юзер видит конкретную ценность («подскажу по белку») за 15 сек screening'а, не «отдай мне 16 ответов».

**Edge cases TIER-A:**

- **Pregnancy / breastfeeding** не учитывается → советы не выдаём вообще, только tracking (соответствует §1 принципу №4). Когда AI видит free-text упоминание беременности — сразу `health_concern_high` нудж + переключение в screening.
- **Eating disorder** — то же самое. Free-text триггер слов типа «*срыв*», «*ненавижу свой вес*» → AI задаёт supportive вопрос, не нудж.
- **BMI<18.5 + goal=lose** — soft warning ladder (Design Doc §4.4) **остаётся в TIER-A** (видим weight + height, можем посчитать BMI без health-flags).

**Action:** обновить Design Doc §4 — выделить TIER-A vs TIER-B, переместить health screening из «анкета на входе» в «gate перед советами».

## R4. Скан еды — Design Doc целиком

**Spec v1 (§7):**
> Похоже на пасту с курицей 🍝 ~520 ккал. Кнопки: `[Добавить] [Не то]`. После добавления: `Записала ✅ Сегодня ты уже на 40% нормы`. Кнопки: `[Добавить воду] [Посмотреть день]`.

**Design Doc (§5):**
> Edit-message loading (`👀 Распознаю...` → edit на результат). Confidence routing (≥0.7 / 0.3-0.7 / <0.3 / is_food=false). Hybrid формат с дневным счётчиком + БЖУ. Дисклеймер `±15-20%` только в первом фото. Correction flow (порция / другое блюдо / ингредиент / удалить).

**Решение: Design Doc целиком.**

**Почему:**

1. **Edit-message loading** (Design §5.1) — критично для воспринимаемой скорости при vision p95 = 10 сек. Без него юзер думает что бот завис. Spec v1 этот механизм не упоминает — упустила.
2. **Confidence routing** — Spec v1 рендерит уверенный best-guess всегда. На реальных фото confidence распределение: ~40% high / ~50% medium / ~10% low. Без routing'а медианные кейсы получают ложно-уверенный ответ → юзер теряет доверие после первого мисса.
3. **`[Не то]` Spec v1 = плоская кнопка без correction flow.** Design §5.4 даёт 4 пути коррекции (порция / другое блюдо / ингредиент / удалить) — это покрывает **реальные** жалобы. `[Не то]` в Spec v1 ведёт куда?
4. **БЖУ в формате (Design §5.3):** `≈520 ккал · Б 35 · Ж 18 · У 55` — Spec v1 показывает только ккал. Для аудитории 35-45 ж с goal=lose белок критичен (low_protein — pattern №2 в Design §10.9). Скрывать БЖУ = терять product value.

**Spec v1 даёт одно полезное:** после `[Добавить]` показ кнопок `[Добавить воду][Посмотреть день]` — это next-step nudging, **в Design Doc §5 не описано явно**.

**Уточнение к Design Doc §5.3:** после успешного `add_food_entry` ответ-карточка получает 2 кнопки:

```
🍝 Паста с курицей и томатами
≈520 ккал · Б 35 · Ж 18 · У 55

📊 Сегодня: 820 / 1450
   Б 58 / 110 · Ж 32 / 50 · У 78 / 145

[💧 Добавить воду]   [📊 Посмотреть день]
```

**Action:** добавить footer-buttons в Design §5.3.

## R5. AI Аватар (Flow 8) — Backlog Phase 4

**Spec v1 (§12):**
> Хочешь покажу, как ты будешь выглядеть через 30 дней? `[🔥 Хочу увидеть результат]`. После генерации: «*Вот твой возможный результат 💫*» + `[Хочу так же][Записаться]`.

**Design Doc:** не упомянуто.

**Решение: Backlog Phase 4. Не в Phase 3.**

**Почему:**

1. **Privacy / 152-ФЗ.** Юзер шлёт селфи → AI генерит «через 30 дней». Это **обработка биометрии** (фото лица) → требует отдельный consent + storage policy + retention. На фоне того что текущие consent'ы (food_scanner, nutrition_disclaimer) уже сложно собирать — добавлять третий = дробить Phase 3 в неработающую заглушку.
2. **Cost & latency.** Image-to-image generation (например через Stable Diffusion / DALL-E 3) — ~$0.04-0.10/image, 10-30 сек. На p95 = ~30s = плохой UX. Будет dropoff на «*пока думаю*».
3. **Validity risk.** «*Через 30 дней с -10% веса*» — это **обещание медицинского результата**. Юр-риск выше: ФАС / Роспотребнадзор могут квалифицировать как недостоверную рекламу медуслуг. На сайт уже распространяются ограничения «*Реклама медицинских услуг*» (см. CLAUDE.md «Запрещённые действия»).
4. **Не критично для core loop.** Phase 3 design выдаёт wow-моменты через: фото-распознавание (Flow 5) + дневной отчёт (Flow 6) + cross-promo data-driven (§4.6 mes 2). AI-аватар — bonus wow, не foundation.

**Когда возвращаемся:**

- Phase 4 — после стабилизации nutrition core loop (Phase 3.1+3.2+3.3 в проде)
- Юр-проверка с дисклеймером «*визуализация, не медицинский прогноз*»
- Storage policy: 30 дней TTL, явный consent с правом удаления
- Cost tier — full-vision только для платных юзеров? (subscription decision blocked by business)

**Action:** добавить «AI Аватар» в Open Questions §16 Design Doc как «Backlog Phase 4 — требует юр-проверки».

## R6. Кросс-промо — Design Doc, **уточнение** триггеров

**Spec v1 (§10):**
> Триггеры: жалобы пользователя; паттерны; регулярное использование. Ответ: «*По твоим данным сейчас лучше всего подойдёт: антицеллюлитный массаж + аппарат*».

**Design Doc (§10.2 + §1 принцип 8):**
> `cross_promo` нудж: class=marketing, priority=20, trigger = commitment 21+ дней + goal=tone or signal. Cap: 0/день, 1 раз / 60 дней.

**Решение: Design Doc, но с дополнением списка триггеров.**

**Почему:**

1. **Spec v1 «жалобы пользователя»** — уже покрыто `health_concern_*` + `recommend_services` tool из Phase 2.4 (consultative). Это разговорный путь, не нудж.
2. **«Паттерны»** — Spec v1 не уточняет какие. Design §10.9 (PatternRule seed) даёт 7 паттернов, но они нацелены на nutrition advice, **не** на cross-promo. Нужно **отдельное mapping** «*паттерн → подходящая услуга*» (если делаем).
3. **«Регулярное использование» = Design §1 принцип 8 «commitment»** — то же самое, formal'но (21+ день дневника).

**Уточнение Design Doc §10.2 — расширить триггеры `cross_promo`:**

| Условие | Услуга | Обоснование |
|---|---|---|
| commitment ≥ 21 дн + goal=tone | антицеллюлитный + аппарат | базовый от Design |
| commitment ≥ 14 дн + low_water pattern (4+ из 7) | лимфодренаж | water deficit ↔ lymph stagnation |
| commitment ≥ 14 дн + meal_skips pattern | антистресс / спа-уход | стресс-eating сигнал |
| commitment ≥ 30 дн + достижение цели (вес ↓ ≥3 кг) | поддерживающий массаж | retention для уже мотивированных |
| free-text упоминание «*спина болит*» / «*шея*» | массаж спины | conversational, не нудж |

Все правила сохраняют **cap 1 раз / 60 дней per class**. Mapping живёт в `PatternRule` extension или новой таблице `CrossPromoRule(pattern, service, min_commitment_days, copy_template)`.

**Action:** добавить `CrossPromoRule` в Design §3 (модели) **или** оставить hard-coded в `nudges/dispatcher_general.py` для MVP — open question, решить при декомпозиции в T-задачи.

## R7. Free-text вода через чат — совпадает

**Spec v1 (§8):**
> Пользователь пишет «*выпила кофе*». Ответ: `Записала ☕ ~188 мл воды`. Кнопки: `[+250 мл][Добавить ещё]`.

**Design Doc (§7.2):**
> `parse_beverage(text) → {beverage_slug, ml}`. Regex по `Beverage.aliases` → fallback gpt-4o-mini → расчёт `water_ml = ml × water_coefficient`.

**Решение: совпадает — нет конфликта.**

Spec v1 даёт пример `188 мл` — это `250 × 0.75` (крепкий кофе ≥300мг/день). В Design §8 BHI таблица: `kofe_chernyi water_coefficient = 1.00` для умеренного, `0.75` только для крепкого >300мг. Spec v1 нечётко применяет коэффициент — Design корректнее.

Persistent reply-keyboard `[📸 Фото][💧 Вода][📋 Меню]` (Design §7.1) **не противоречит** Spec v1 — Spec v1 просто не упоминает persistent keyboard вообще, но не запрещает (это не «главное меню», это action toolbar).

**Action:** ничего, оставляем Design §7 как есть.

## 3. Что меняется в Phase 3 MVP scope

**Текущий scope MVP (Design §16 open question 1):**
> онбординг + фото + дневной отчёт + вода + 3-4 базовых нуджа.

**После reconciliation:**

| Phase | Содержание |
|---|---|
| **3.1 MVP** | Welcome 3-кнопочный + TIER-A анкета (5 шагов) + фото (edit-loading + confidence routing + correction) + персистент keyboard + вода (4 кнопки + free-text + soft-delete) + дневной отчёт (push 21:00 + `/день` + inline) + 3 нуджа: `weekly_unlock`, `reengagement`, `booking_continuation` |
